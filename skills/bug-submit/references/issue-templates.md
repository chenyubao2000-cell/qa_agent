# Issue 描述模板

## 语言要求：讲人话，不堆技术黑话

提交 issue 描述和补充评论都要遵守，尤其是代码扫描类 bug（没有人工复现步骤，最容易写得让人看不懂）：

- 不出现未经解释的术语（如"静默丢弃"、"归类"、"兜底逻辑"、"回填"、"命中排除名单"、"全文件"）。如果非用不可，先用一句话讲清楚"具体在哪个环节发生了什么、造成用户能看到/看不到什么结果"，再用这个词。
- **"实际结果"必须代入一个具体例子**，说人话描述用户/PM 能观察到的现象（数据里少了什么字段、页面上显示了什么/没显示什么），不要停留在代码内部变量名或函数名层面。
- 没有真实用户操作路径的代码扫描类 bug，"复现步骤"改写成"触发条件"，同样要讲清楚是什么样的真实数据会触发（举一个具体的数据例子），而不是只描述代码分支条件。
- 提交前自查一遍：把描述读给没看过这段代码的人，能不能听懂"坏在哪、影响是什么"——听不懂就要重写。
- **不要暴露"这是特意讲人话写的"**：描述和评论里禁止出现任何自我说明性的话（如"已用通俗语言改写""大白话版""本条已简化表达"之类），直接把它写成本来就该有的正常技术描述，让人看不出这是刻意处理过的。

❌ 反面例子：`该身份信息直接从 bridge_keys 消失`

✅ 正面例子：`候选人如果在 GitHub 主页的 blog 一栏填的其实是自己的 Twitter 链接，系统抓取资料后，候选人的社交账号列表里不会出现这个 Twitter 账号——招聘顾问在系统里看不到，只有去 GitHub 主页才能看到。`

## 单个 bug

```
🔗 Task：{shareUrl}
（仅当本次 bug 关联到某个具体 task 时加这一行——用户提供的 task，或你为验证自己新建触发的 task 都算，规则见 SKILL.md「1.5 Task 关联」。不涉及具体 task 就删掉这一行，不要留空占位）

## 复现步骤
1. 进入 [具体页面]
2. [点击/输入/操作]
3. [下一步操作]

## 预期结果
[正常情况下应该发生什么]

## 实际结果
[实际出现了什么，代入具体例子，说人话——数据里少了什么/页面上看到了什么，不用代码里的变量名或黑话]

-----------

## 代码分析

**涉及文件：**
- `path/to/file.ts`（L行号）：[这段代码的问题是什么]
- `path/to/file2.ts`（L行号）：[这段代码的问题是什么]

**根因链：**
1. [触发点]
2. [中间传导]
3. [最终表现]

**代码证据：**
（贴出有问题的关键代码片段，用注释标出问题所在）

## 最优解决方案

**修改 `path/to/file.ts`：**
（贴出具体修改方案，越具体越好）
```

## 合并多个相似 bug

用于「Step 2：读代码验证 + 排查相似 Bug」发现同页面/同类功能中存在相同根因的多个 bug 时，合并为一个 issue：

```
## Bug 1：[功能A] 具体现象

### 复现步骤
1.
2.

### 预期结果 / 实际结果

---

## Bug 2：[功能B] 具体现象

### 复现步骤
1.
2.

### 预期结果 / 实际结果

-----------

## 代码分析

**共同根因：**
[说明为什么这些 bug 同根同源]

**涉及文件：**
- `path/to/file.ts`（L行号）：[问题]

**根因链：**
1.
2.

**代码证据：**

## 最优解决方案

（统一修复方案）
```

标题反映共同问题，不要只用其中一个子 bug 的现象当标题。
