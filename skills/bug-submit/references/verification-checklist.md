# 验证判断标准

## 强制要求

必须先读代码，从代码层面确认 bug 真实存在，才能提交。禁止仅凭用户描述的现象直接提交。

## 三种结论

在代码库路径（`.env` 的 `SOURCE_PROJECT_DIR`，当前为 `D:\code\mira`；`Read`/`Grep`/`Glob` 不做 shell 变量展开，需先读 `.env` 拿字面值）中找到相关页面/组件的代码，仔细阅读逻辑后，落到以下三种之一：

1. **能从代码中确认问题** → 继续提交。代码分析部分必须包含：
   - 具体文件路径 + 行号
   - 有问题的代码片段原文
   - 根因链说明（触发点 → 中间传导 → 最终表现）
   - 判定本次 bug 的修复层级（前端 / 后端 / 前后端都要改），供提交时分配 assignee 用
2. **无法从代码确认**（找不到相关代码、逻辑正常、无法复现路径） → 明确告知用户"从代码中无法确认该问题存在"，说明原因，询问是否仍要提交
3. **代码逻辑正常但产品设计有争议** → 说明代码当前行为，让用户判断是否属于 bug

## 能手动复现的必须实际验证

如果 bug 涉及接口调用、数据查询等可直接执行的操作，不要仅靠读代码推断——用 curl / fetch 实际调一下，把真实的响应结果贴进 issue。这样可以精确定位问题（比如哪个字段值重复、哪个入参触发异常），也能帮助排查根因。

## 涉及数据库的 bug 必须查库验证

如果 bug 与数据库数据状态有关（如字段值异常、记录缺失、写入错误、数据不一致等），必须用 `mcp__postgres__query` 直接查询数据库，把真实的 SQL 结果贴进 issue。禁止仅凭代码推断数据库状态。

## 只报用户能真实复现的 bug

所有 bug 必须能通过正常的前端页面操作触发，不考虑"绕过前端直接调用后端接口"的场景。如果一个问题只有直接请求 API 才能复现，而正常用户操作不会触发，则忽略不提。

## 排查相似 bug

同时主动排查：同页面或同类功能中是否存在相同根因的其他 bug（如同一个组件缺陷影响多个 section，或同一个工具函数被多处错误使用）。

- 发现相似 bug → 合并为一个 issue（模板见 `issue-templates.md` 的「合并多个相似 bug」部分）
- 未发现相似 bug → 按单个 bug 正常提交
